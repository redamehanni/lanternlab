Lantern Engine — Analyse d’architecture

Moteur ARG data-driven pour des centaines de Lanternes, administrable sans développement.

Date : 9 août 2026 · Statut : analyse (pré-implémentation) · Destinataires : Reda / Adam
Alignement : FD-000 (surface compose, organe décide) · Ne confond pas Event Engine « QR→badge » et aventure ARG

1. Constat d’existant (ce qui ne doit pas être confondu)

Aujourd’hui dans le dépôt :

  • Porte Lanternes = surface Deuxième Âme (mobile/src/data/deuxiemeAme.js, FD-004) — seule Porte open.
  • Event Engine type: lanterne = événement découvrable QR → journal + badge Wallet. Ce n’est pas une aventure ARG.
  • LanternsScreen = scène visuelle Lantype (DA), scan orphelin.
  • Aucun modèle ARG, Atelier, Item Média, équipe Lanterne, ni Lantern Lab.
Décision d’architecture retenue : créer un nouvel organe Lantern Engine, distinct de l’Event Engine. L’Event Engine peut rester un canal d’entrée (balise / découverte publique) ou être branché plus tard comme déclencheur QR générique — jamais comme stockage de l’aventure.

Alignement FD-000 : surface compose, organe décide ; Material Lab / Lantype = présentation verre uniquement — interdit d’y mettre du métier Lanterne.

2. Modèle mental : définition vs runtime

Séparer deux plans dès le jour 1 (sinon explosion à N = 100+) :

PlanContenuQui écritQui lit
Definition (publiée) Histoire, médias, triggers, horaires, corrigé, rewards Lantern Lab → API publish Clients (snapshot versionné)
Runtime (joueur / équipe) Progression, médias débloqués, appels manqués, team Mobile + moteur Joueur / équipe

Règle d’or : aucune branche if (lanternId === 'pont-neuf') dans le code. Tout comportement = évaluation de règles déclaratives + état runtime.

Abstractions recommandées (noyau générique)

  1. LanternDefinition — document versionné (id, kind: main|bonus, version, status: draft|published|archived).
  2. MediaContent — payload neutre (video|audio|image|text|rich, URI, durée…).
  3. MediaItem — représentation immersive (skin: vhs|dictaphone|letter|…) + ref Content + politique (imposed|displayed|unlockable) + lifespan.
  4. Trigger — règle déclarative (type, params, effects[]).
  5. Effect — mutation runtime (unlockMedia, ringPhone, setFlag, advanceStep, grantReward…).
  6. SchedulePolicy — temps (once, daily, dateRange, timezone, missPolicy).
  7. AtelierLayout — slots de cartes verre : shell fixe, contenu injecté.
  8. PermanentObject — téléphone, radio… = players + ports de déclenchement.
  9. CorrectedSheet — fiche post-aventure, gated par completed.
  10. TeamSession — équipe liée à une instance (chat via Communication).

3. Parcours utilisateur (contrat de navigation)

Deuxième Âme → Univers Lanternes → Sélection (en cours | terminées) → Transition → Porte Rouge (code) → Atelier
  • En cours / disponible : résumé + rewards → démarre instance runtime → Porte.
  • Terminée : jamais rejouable ; ouvre le corrigé (pas la Porte).
  • Listes UI distinctes : principales vs bonus (filtre sur kind, pas deux moteurs).

Porte Rouge = gate d’accès Atelier (code hashé serveur, rate-limit). L’Atelier = une seule scène shell ; les cartes verre (Material Lab sync) sont la surface du tableau de bord.

4. Items Média & états — modèle robuste

MediaContent → MediaItem (skin + policy) → PlayerMediaState
  • Imposé : Atelier en lockNavigation jusqu’à media.completed.
  • Affiché : visible dès atelier.entered.
  • Déblocable : invisible jusqu’à Effect unlockMedia ; section « Découverts ».
  • Lifespan : illimité ou borné (durée / date / trigger) — horloge serveur + sync.

Piège à éviter : coupler skin et fichier dans un seul blob — empêche la réutilisation et casse le Lab.

5. Déclencheurs — faisabilité technique

TriggerFaisable ?ArchitectureLimites
QR Oui (déjà partiel) Token signé → API triggers → Effects Anti-rejeu, tokens rotatifs
NFC Oui (plus tard) Même contrat que QR (beaconId) iOS limité ; fallback QR obligatoire
GPS Oui avec nuances Zone + expo-location + validation Haversine serveur Background fragile ; drift urbain
Heure / appels Oui SchedulePolicy + job serveur + push Fuseau ; miss selon politique
Radio géo Oui en simulation Catalog frequency + zoneId → MediaContent Pas de vraie FM

GPS « assez fiable » pour ARG urbain si : enter + confirmation UX ; validation serveur ; hysteresis ; unlocks critiques en QR/NFC primaire, GPS secondaire.

Radio : ne pas viser le broadcast Hertz. Objet permanent Tuner + table de fréquences versionnée. Le GPS choisit la ligne active.

Appels : objet téléphone + CallCue (schedule + audio + missPolicy). Sonnerie si Atelier ouvert ; sinon push optionnelle.

6. Joueurs, équipes, carte

  • Joueur : user Ma Zone + LanternProfile.
  • Équipe : avant start → créer ou réutiliser dernière équipe → TeamSession.
  • Chat : réutiliser l’organe Communication avec lifecycle lantern_team (pas un 2ᵉ chat).
  • Carte V1 : partage volontaire de last known position — pas de tracking temps réel.

7. Lantern Lab (outil admin)

Produit data-only (module admin) pour concepteurs non développeurs :

  • CRUD Definition + publish (version bump immutable).
  • Éditeurs : médias → Content ; binding Item ; graphe Triggers→Effects ; schedules ; code Porte ; corrigé ; kind ; statut.
  • Vue globale : graphe + timeline des schedules.
  • Preview dry-run du runtime.

Publier = snapshot versionné consommable par le mobile. Jamais de hot-patch de logique.

8. Points faibles & risques à l’échelle

  1. Surcharger l’Event Engine avec l’ARG → dette. Mitigé par organe dédié.
  2. État runtime client-only → triche / désync. Vérité serveur.
  3. Médias lourds sans CDN → coût. Lazy download + TTL.
  4. Triggers temporels sans job → appels aléatoirement « perdus ». Scheduler + missPolicy.
  5. GPS comme unique gate → frustration. Fallback balise pour nœuds critiques.
  6. Explosion de skins dans le code. Catalogue assets versionné.
  7. Équipes / chat sans confinement. Lifecycle dédié + archive.
  8. Corrigé / spoiler trop tôt. Endpoint gated.
  9. Non-rejouabilité molle. Run unique terminal.
  10. Lab sans validation. JSON Schema + lint graphe.

9. Améliorations qui renforcent sans changer la vision

  • Event sourcing léger (lantern_journal append-only) pour audit et idempotence.
  • Feature flags de Definition (gps, nfc, radio) pour dégradation device.
  • Deux listes UI = un seul query kind + runtime.status.
  • Porte Rouge : hash + rate limit ; option code d’équipe plus tard.
  • Atelier : contrat CardSlot ; cartes verre Lantype = pure présentation.
  • Compat balise existante via Effect importDiscoverBadge sans fusionner les modèles.

10. Découpage de livraison recommandé

  1. E0 — Modèle Definition + Runtime + schéma + tests organe (aucune UI aventure).
  2. E1 — Shell : sélection main/bonus → Porte Rouge → Atelier + média imposé.
  3. E2 — Items Média (3 états + lifespan) + téléphone (appels schedule).
  4. E3 — Triggers QR (+ NFC stub) + GPS enter confirmé.
  5. E4 — Équipes + chat lantern_team + carte last-known.
  6. E5 — Radio tuner géo-simulé.
  7. E6 — Corrigé + non-rejouabilité.
  8. E7 — Lantern Lab (publish + graphe + lint) — bloqueur culturel : plus aucune Lanterne créée en code.

11. Verdict

La vision est cohérente et tenable si on la traite comme un moteur data-driven (Definition / Runtime / Triggers / Effects / MediaContent ≠ Item), pas comme une collection d’écrans spéciaux.

Les zones délicates ne sont pas conceptuelles mais opérationnelles : GPS en fond, schedules fiables, anti-triche serveur, catalogue de skins, et discipline absolue « zéro logique par Lanterne dans le code ».

Le Lantern Lab n’est pas un nice-to-have : c’est la condition de passage à l’échelle vers des centaines d’aventures.
