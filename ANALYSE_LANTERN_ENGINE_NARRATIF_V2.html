Lantern Engine narratif & Lantern Lab

De Trigger → Effect à un moteur de logique narrative générique — atelier du Bâtisseur.

Date : 9 août 2026 · Statut : analyse (pré-implémentation) · Destinataires : Reda / Adam
Complète : ANALYSE_ARCHITECTURE_LANTERN_ENGINE · Conserve Definition / Runtime · MediaContent ≠ MediaItem
Principe : aucune branche if (lanternId === …) — une Lanterne = données versionnées, pas du code.

1. Verdict

Les fondations de l’analyse du 9 août restent valides : organe Lantern Engine distinct de l’Event Engine, séparation Definition / Runtime, MediaContent ≠ MediaItem, Atelier shell, objets permanents, Porte Rouge, SchedulePolicy, bridge badge.

La limite Trigger → Effect ne suffit plus. On introduit une couche Story / State Engine dont l’unité d’exécution est la Rule :

Événement / Trigger → mise à jour d’état → évaluation des conditions (AND / OR / NOT) → exécution d’actions ordonnées
Décisions figées pour validation : Lab = app web lantern-lab/ (≠ Material Lab lantype-lab/) ; évaluation serveur-autoritaire ; Rule = vérité logique ; Arbre de Situation = projection éditable + layout (pas un second moteur) ; scopes d’état : player | team | run.

3. Exemple central — Talkie Magellan

Item Média « Talkie-Walkie » découvert rue Magellan. Même événement, expériences différentes selon zone + fenêtre horaire. Le moteur ne connaît ni Monsieur X, ni Monsieur Y, ni Madame V — uniquement des briques génériques.

RuleConditions (ET)Actions
A Talkie découvert · zone 11e|13e · 17h00–17h15 Sonner talkie → audio Monsieur X
B Talkie découvert · zone 1er|3e · 17h00–17h15 Sonner talkie → audio Monsieur Y
C Talkie découvert · zone 7e|17e · 17h00–17h15 Sonner talkie → audio Madame V

Implémentation données : 3 Rules avec le même listen: ['media.discovered'], conditions de zones différentes, actions audio différentes. Si le modèle ne peut pas exprimer Magellan sans code spécifique, l’architecture est refusée.

4. Modèle Condition

4.1 AST

ConditionExpr = | { op: 'true' } | { op: 'and', children: ConditionExpr[] } // ET | { op: 'or', children: ConditionExpr[] } // OU | { op: 'not', child: ConditionExpr } // NON | Predicate // feuille

Groupes imbriqués = nesting naturel. Exemple Magellan (11e / 13e) :

{ "op": "and", "children": [ { "type": "media.discovered", "mediaItemId": "talkie_magellan" }, { "type": "geo.inAnyZone", "zoneIds": ["arr_11", "arr_13"] }, { "type": "time.inWindow", "start": "17:00", "end": "17:15", "timezone": "Europe/Paris" } ] }

6. Modèle Variable

VariableDef = { id, label, valueType: 'boolean' | 'number' | 'string' | 'enum', enumValues?, defaultValue, scope: 'player' | 'team' | 'run' }

8. Rule & moteur d’évaluation

Rule = { id, title, enabled, priority, situationId?, // grouping Arbre listen: string[], // event types candidats condition: ConditionExpr, actions: Action[], occurrence: OccurrencePolicy }

8.1 Boucle

handleEvent(event, def, runtime): 1. INTRINSIC_UPDATE (media, beacon, geo, journal) 2. CANDIDATES = rules enabled ∩ listen ∩ occurrence OK 3. Sort priority desc, id asc 4. Pour chaque candidate : si eval(condition, Context) → mark + executeActions 5. RECURSE events émis (depthMax ≈ 8, ruleFireBudget) 6. Persist runtime + ActionPlan → mobile

EvalContext = { definition, runtime, event, now, lat, lng, resolvedZones[] } — identique en production et en simulateur. Déterminisme : mêmes entrées → mêmes Actions. Timezone par défaut Europe/Paris.

9. AND / OR / NOT

  • and : tous vrais (enfants vides = true)
  • or : au moins un vrai (enfants vides = false)
  • not : inverse
  • Short-circuit autorisé ; le simulateur journalise chaque feuille (✓ / ✗)

Pas de DSL texte obligatoire. Le Lab édite l’AST via groupes + briques.

10. Temps, GPS, QR / NFC, unique / récurrent

10.1 SchedulePolicy

SchedulePolicy = { mode: 'once' | 'daily' | 'weekly' | 'dateRange', timezone, at?, window?, daysOfWeek?, startDate?, endDate?, missPolicy: 'expire' | 'skip_wait_next' | 'deliver_late' }

Job serveur (cron minute) + ledger occurrenceLedger[ruleId] : lastFiredAt, missedAt[], nextDueAt, exhausted.

Appel 20h17 unique : Note consultée + Cassette consommée + zone Bureau + heure 20h17 + appel_20h17_deja_recu = false → sonner téléphone → audio → var.set true. Si absent : missPolicy: expire → événement manqué, non récupérable. Si quotidien : daily + skip_wait_next → prochaine occurrence.

10.2 GeoZone

GeoZone = { id, label, kind: 'circle' | 'polygon' | 'arrondissement' // circle: center + radiusM // polygon: coordinates // arrondissement: Paris 1..20 }

Mobile envoie la position ; serveur revalide (Haversine + polygones). Pas de geofence OS obligatoire en v1 (polling / heartbeat).

10.3 Beacon

Beacon = { id, channel: 'qr' | 'nfc', tokenId opaque, bindsTo?: { mediaItemId?, placeLabel? } }

Scan → POST /api/lanterns/:runId/events. NFC = même contrat (stub). Bridge Event Engine via Action badge.importDiscover.

10.4 OccurrencePolicy

OccurrencePolicy = { kind: 'always' | 'once_per_run' | 'once_per_player' | 'once_per_team' | 'once_per_occurrence' | 'daily' | 'cron', schedule?, missPolicy?, maxFires? }

11. Lantern Lab — atelier du Bâtisseur

App web lantern-lab/ (Vite/React), auth admin. Ce n’est pas le Material Lab (lantype-lab/ = DA verre uniquement).

11.1 Shell

  • Barre projet : titre, kind, status, version, Publish, Lint
  • Rail gauche : Médias, Items, Zones, Beacons, Variables, Objets, Équipe
  • Centre : vues à onglets
  • Droite : Inspecteur contextuel (toujours visible)

11.2 Onglets

  1. Histoire / Étapes / Objectifs
  2. Arbre de Situation — conception logique principale
  3. Timeline — fenêtres, appels, expirations, récurrences
  4. Carte — QR, NFC, zones GPS, POI
  5. Médias — Content ↔ Item ↔ Rules
  6. Simulateur — état joueur injecté → SIMULER → trace
  7. Audit (diagnostics)
  8. Publication / Archivage / Corrigé / Porte Rouge

12. Arbre de Situation

Projection éditable des Rules + layout. Pas une seconde source de vérité.

Situation = { id, label, kind: beat|branch|gate|action_chain|start|end, ruleIds[], parentId?, position {x,y} } SituationEdge = { from, to, label?, derivedFrom? }
TALKIE DÉCOUVERT │ ▼ HEURE 17h00–17h15 ? │ ▼ QUELLE ZONE ? ├── 1er / 3e → Monsieur Y ├── 7e / 17e → Madame V └── 11e / 13e → Monsieur X

Clic nœud → Inspecteur : id, type, conditions, actions, médias, variables, horaires, zones, dépendances. Le créateur modifie la Rule sous-jacente.

13. Timeline, Carte, Vue Médias, Simulateur

  • Timeline : événements ponctuels / récurrents, appels téléphone & talkie, radio, médias temporaires, expirations, fenêtres horaires.
  • Carte : balises QR/NFC, zones GPS, lieux, déclencheurs géo, zones radio.
  • Médias : type, Item, état, déclencheur, durée, conditions, actions liées.
  • Simulateur : position, heure, date, étape, médias, variables, choix, équipe → même moteur d’eval, source: lab_sim, trace feuille par feuille + ActionPlan. Pas de Wallet / push réels.

14. Liaison des vues — SelectionContext

Objet partagé { ruleId?, mediaItemId?, zoneId?, beaconId?, situationId?, timeCursor? }. Une sélection dans une vue met en évidence les entités liées partout ailleurs. Un seul Inspecteur — pas de formulaires dupliqués divergents.

Publish bloqué si diagnostics error. Filet runtime : depthMax + ruleFireBudget.

Boucles : graphe Rule A → Rule B si une Action de A peut émettre un Event écouté par B. Cycle sans garde = erreur bloquante.

16. Versioning & évolution sans casser

LanternDefinition { id, slug, kind: main|bonus, engineSchemaVersion, // breaking moteur contentVersion, // incrément publish status: draft|published|archived, // media, items, zones, beacons, variables, // rules, situations, atelier, porte, corrigé… }
  • Draft mutable · Publish = snapshot immuable · Runs pinés sur leur contentVersion
  • Registres predicates / actions versionnés (introducedInSchema, deprecatedInSchema)
  • Fail-soft sur types inconnus · migrations Lab « Upgrade definition »
  • Golden tests : fixtures Magellan + Appel 20h17 (données, pas code Lanterne)

17. Lisibilité à grande complexité

  • Situations = chapitres (collapse, focus sous-arbre, breadcrumb)
  • Filtres : média, zone, fenêtre, variable, type trigger
  • Recherche globale · mode lecture vs technique
  • Edges en langage naturel (« 11e ou 13e »)
  • Templates de patterns (fenêtre+zone+audio ; appel unique ; NFC unlock)
  • Warning si trop de Rules sans Situation parente

20. Principe directeur

Le développeur construit le moteur générique (predicates, actions, eval, lint).

Le créateur construit les aventures dans le Lantern Lab — sans jamais demander « programme une condition spéciale pour la Lanterne 27 ».

Le Lantern Engine doit être assez puissant pour des ARG complexes ; le Lantern Lab assez intuitif pour que le Bâtisseur les compose. Une nouvelle Lanterne = une nouvelle Definition publiée — jamais une nouvelle fonctionnalité codée.

Aucune implémentation avant validation explicite de cette architecture V2.
